# Звіт по проекту: "Сервіс Конференцій" (Conference Service)

## Вступ до проекту
Проект являє собою спрощений веб-сервіс для проведення онлайн-конференцій. Він дозволяє користувачам створювати "кімнати" (rooms), приєднуватися до них, вести текстовий чат в реальному часі та встановлювати відеозв’язок один з одним за технологією WebRTC. Всі історичні дані (кімнати, активні та неактивні учасники, повідомлення) зберігаються у базі даних (MongoDB), щоб забезпечити консистентність та стійкість системи, тоді як поточна оперативна взаємодія (сигналінг, чат) відбувається миттєво через WebSockets.

В основі архітектури лежить поєднання:
- **REST API** для базового керування сутностями (створення, приєднання до кімнати).
- **WebSocket Server** для сповіщень у реальному часі та обміну WebRTC-сигналінгом.
- **WebRTC** для Peer-to-Peer потокового медіа безкосередньо між браузерами.
- **MongoDB** для персистентності.

## Головні блоки коду та їх функціонал

Структура проекту розділяється на дві великі частини: серверну (Backend) та клієнтську (Frontend).

### 1. Серверна частина (`server/`)
Сервер відповідає за бізнес-логіку підключень, збереження даних та сигналінг.

- **`server/index.js`**
  Головний вхідний файл програми. Він запускає Express-сервер для обробки REST API, інтегрує статичні файли клієнта, здійснює підключення до бази даних і підіймає WebSocket-сервер для обробки з'єднань в реальному часі на порту 3000. В ньому ж закріпляються всі маршрути (routes).

- **Директорія `server/models/`** (Схеми бази даних)
  Містить Mongoose-моделі для роботи з колекціями бази даних:
  - `Room.js` — збереження інформації про створені кімнати.
  - `Participant.js` — відстеження учасників (користувачів в кімнаті з мітками підключення та виходу `left_at`).
  - `Message.js` — збереження історії чату.

- **Директорія `server/routes/`** (REST API)
  Тут знаходяться обробники HTTP-запитів до сервісу:
  - `rooms.js` — ендпоінти створення нової кімнати, отримання списку кімнат, закриття та видалення кімнат.
  - `participants.js` — ендпоінти для входу (`join`) та виходу (`leave`) з кімнати.
  - `messages.js` — отримання історії повідомлень в конкретній кімнаті.

- **Директорія `server/ws/`** (Real-time події)
  Відповідає за обробку подій WebSocket:
  - `handler.js` та `broadcaster.js` — керують розсилкою повідомлень всім клієнтам обраної кімнати (чат, події входу/виходу), а також здійснюють ретрансляцію повідомлень WebRTC (`webrtc_offer`, `webrtc_answer`, `webrtc_ice`) для встановлення P2P зв'язку користувачів.

### 2. Клієнтська частина (`client/`)
Клієнт надає інтерактивний користувацький інтерфейс, написаний за допомогою HTML/CSS та Vanilla JavaScript.

- **`client/index.html` та `client/js/lobby.js`**
  Головна сторінка-лобі. Відповідає за відображення поточного списку кімнат (отриманого по REST), створення нових кімнат та дозволяє користувачу ввести своє ім'я для приєднання (викликаючи POST `/join`).

- **`client/room.html` та `client/js/room.js`**
  Сторінка власне самої конференції. `room.js` інтегрує всі інші підмодулі (вебсокети, WebRTC) і організовує роботу інтерфейсу (відображення панелі учасників, вікна чату, кнопок керування медіа та сітки веб-камер).

- **`client/js/ws.js`**
  Огорнутий клас WebSocket-клієнта. Займається підключенням до `/ws`, автоматичним перепідключенням (backoff), перехопленням подій чату, системних подій (`user_joined`, `user_left`) і передачею сигналінгу для WebRTC.

- **`client/js/webrtc.js`**
  Оброблює всю логіку WebRTC. Взаємодіє з API камери браузера (`getUserMedia`), створює `RTCPeerConnection` для кожного іншого учасника кімнати. Встановлює P2P потоки, створює офери/ансвери та обмінюється ICE-кандидатами через WebSocket-систему (яка тут відіграє роль Signaling-сервера).

## Життєвий цикл системи (Аналіз діаграми `SequenceDiagram.puml`)

На основі UML діаграми послідовностей, можна так описати робочий цикл кімнати:

1. **Створення і Приєднання (REST):** Користувач заходить в лобі, ініціює створення кімнати. Надалі він та інші користувачі відсилають HTTP POST запит щоб приєднатися до кімнати (`/join`). Сервер реєструє учасника у базі даних (Participant) і повертає `participantId`.
2. **Активація Real-Time Зв'язку (WebSocket):** Одразу після успішного підключення до кімнати, клієнт відкриває WebSocket з'єднання із сервером і відправляє подію `ws_join`. Сервер повідомляє усіх присутніх про появу нового учасника подіями `participants_list` / `user_joined`.
3. **Історія чату (REST + WS):** Клієнт завантажує попередню історію чату використовуючи REST `GET /messages?limit=50`. Після цього всі наступні текстові повідомлення пересилаються безпосередньо через WebSocket для миттєвого збереження в БД та відображення іншим (broadcasting `chat_message`).
4. **Ініціалізація Конференції (WebRTC):** Коли користувачі бажають почати дзвінок, вони активують свої камери. Їх браузери створюють об'єкт PeerConnection і передають SDP пакети інформації (`Offer` та `Answer`) по WebSocket до співрозмовника. Після успішного обміну ICE-кандидатами відео та аудіо дані пересилаються **виключно P2P напряму** між браузерами (оминаючи сервер, що дуже заощаджує ресурси).
5. **Вихід із кімнати:** Коли учасник натискає "Покинути" (`Leave`), клієнт відправляє REST запит щоб записати час виходу `left_at` у БД та закриває WebSocket-з'єднання. Сервер через WS відразу ж надсилає `user_left` іншим учасникам, що призводить до відключення його відео у їх інтерфейсах.
